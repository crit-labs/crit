# decode-gemv

Weight-only decode GEMVs from [crit](https://github.com/crit-labs/crit)'s quantized-projections technique: 1 to 16
rows of 16-bit activations times a matrix stored as NVFP4 (W4A16), FP8 E4M3 with one scale per row or MXFP8's E8M0
scale per 32 inputs (W8A16), BF16, or INT4 with a zero point a group (AWQ, GPTQ: W4A16), on CUDA cores with FP32 sums
(one kernel, structure gemv-cuda, the weight format a run option resolved through a decoder trait over the kernel
core's decoders: a new format is a decoder, not a kernel); the same five formats in Triton for 1 to 16 rows (gemv_any,
structure gemv-triton: the format a decoder over the kernel core's crit_kcore.formats, the multiply a path, FP32 sums a
16-value group on the CUDA cores or tl.dot on the values exact in 16 bits), whose NVFP4 fma path for 1 to 8 rows
(gemv_triton) and FP8 dot path for 1 to 16 rows (gemv_fp8_dot) are the Triton GEMVs this kernel had; and the decoders that write an NVFP4 matrix's
values (BF16/FP16, or FP8 rows in units of a row scale) for a provider's GEMM.

**Why it exists.** cuBLASLt does not multiply 16-bit activations by NVFP4 or FP8 weights (its block-scaled and FP8
GEMMs take the narrow format on both operands; flashinfer's mm_bf16_fp4 does W4A16, see the yardsticks), and a
provider's GEMM picks its kernel, and so each output's sum, by the row count: a decode row then changes with the rows
beside it, and batched decoding or a speculative verify window stops matching serial decoding. Here every row reduces
in one fixed order whatever the row count (the rows a warp takes are a choice of speed, never of order), so a row's
result is the same bits alone and beside up to 15 others, and a 16-bit decode row reads each weight once, at about the
device's streaming rate.

## Applicability

| | |
| --- | --- |
| Weight formats | NVFP4: codes [N][K / 2] (element 2i in the low nibble of byte i), E4M3 block scales [N][K / 16] row major, inverse global scale [N] FP32. FP8: E4M3 codes [N][K] with FP32 row scales [N] or E8M0 exponents [N][K / 32] (MXFP8, modelopt's layout). BF16: [N][K]. INT4 with a zero point a group (`gemv_int4`): crit's rows, codes [N][K / 2] unsigned (element 2i in the low nibble of byte i), FP16 scales and uint8 zero points (0 to 16) [N][K / group], a value (code - zero) * scale; `repack_awq` (qweight [K][N / 8] and qzeros in AWQ's 0, 2, 4, 6, 1, 3, 5, 7 nibble order, scales [K / group][N]) and `repack_gptq` (qweight [K / 8][N] packed along K, qzeros with the +1 offset where the checkpoint stores zero - 1, act order's g_idx: the inputs sorted by group, the caller multiplies x[:, perm]) put a checkpoint's tensors there exactly, on the device, through the kernel core's AWQ and GPTQ decoders |
| Activations | BF16 or FP16 [M][K], rows on 16-byte boundaries; M 1 to 16 (CUDA, gemv_any, FP8 dot GEMV), 1 to 8 (Triton NVFP4) |
| FP8 dot GEMV | gemv_fp8_dot(x, w, row_scale, out, fp8_dot_tile(N, K, multiprocessors), partial): a program multiplies a [16 rows x BK] block of the activations by a [BN x BK] block of the E4M3 weights (exact in BF16) with tl.dot, FP32 sums over its part of K; with several parts the programs write FP32 partial sums (dot_partial_elements) and a second kernel adds them in part order and applies the row scale. The program's shape never depends on the call's row count, so a row's bits are the same alone and beside up to 15 others; fp8_dot_tile picks it from the matrix's shape and the multiprocessor count. | Determinism | each row's bits independent of the call's other rows, the same on a repeat; the CUDA and the Triton GEMVs (and gemv-triton's two paths) sum in different orders (within FP32 rounding of each other), so a process keeps to one. Every knob but the order knobs (gemv-nvfp4's WPR, gemv-nvfp4-triton's BLOCK_K, gemv-fp8-dot's plan) gives the same bits; a tuning keeps one value of each order knob a matrix for every row count. ## Structures and knobs

kernel.json lists them; `default` knobs plus `default_rows` run what the kernel ran before it had knobs.

| Structure | What | Knobs (order knobs in bold) |
| --- | --- | --- |
| gemv-cuda | the CUDA-core GEMV for every weight format, 1 to 16 rows; key: weights (0 NVFP4, 1 FP8, 2 MXFP8, 3 BF16, 4 INT4 with a zero point, the codes mma-rows uses), N, K | WARPS, ROWS (0: the format's rule from before the knobs), **WPR**, PREF, STREAM |
| gemv-nvfp4, gemv-fp8, gemv-bf16 | aliases of gemv-cuda for one format with the knobs they had (no bench: sweeps tune gemv-cuda); a tuning made before gemv-cuda still applies: an alias's table wins for its format where it names a configuration other than its defaults, or where the tuning tunes the alias and not gemv-cuda | as before (gemv-nvfp4: WARPS, ROWS, **WPR**, PREF, STREAM; gemv-fp8 and gemv-bf16: WARPS, ROWS, PREF, STREAM) |
| gemv-triton | the Triton GEMV for every weight format, 1 to 16 rows (gemv_any); key: weights (gemv-cuda's codes), N, K. MUL 1 (fma): BN rows a program, BK values a step, one FP32 sum a 16-value group carried over K, the group's factor (NVFP4's E4M3 scale, MXFP8's power of two, INT4's scale) after its sum, the row factor after the row's; eight rows a program, more as further programs. MUL 2 (dot): a [16 x BK] activation block by a [BN x BK] weight block decoded exactly to BF16 (FP16 for FP16 activations on NVFP4 and FP8; INT4 as two dots, the value's BF16 rounding and its rest) with tl.dot, SPLIT parts of K added in part order | **MUL**, **BN**, **BK**, WARPS, STAGES, **SPLIT** (all 0: the rule: dot where K is a multiple of 128 and the values are exact in the dot's type, fma otherwise and for MXFP8; the dot's tile by the multiprocessor count, the fma's by Triton's autotuner on the device) |
| gemv-nvfp4-triton | alias of gemv-triton: NVFP4 on the fma path, 1 to 8 rows (gemv_triton, its bits before the alias: Triton aliases A/B); its tuning still applies to gemv_triton, and to gemv_any on NVFP4 where its table names a configuration other than its defaults, a sweep selected one, or the tuning tunes it and not gemv-triton | BLOCK_N (0: the autotuner over GEMV_TILES), WARPS, STAGES, **BLOCK_K** |
| gemv-fp8-dot | alias of gemv-triton: FP8 on the dot path with BF16 operands, 1 to 16 rows (gemv_fp8_dot, its bits before the alias); its tuning applies the same way | **BN**, **BK**, **WARPS**, **SPLIT** (all 0: fp8_dot_tile's shape rule; one plan a matrix) |
| rows-int-block | the declared integer decode rows (int-block-experts' rows alias it and forward here): 4-bit weights (E2M1 x 2 or INT4, E4M3 per 16) against int8 activations per 16 or 32, a job of 1 to 8 tokens a matrix of a table; the kernel core's declared rows (declared_rows.cuh, multiply.cuh's DeclaredInt); key N (max rows), K (the activations' width) | THREADS, ROWS, STREAM, UNROLL (none changes an output's order) |
| rows-fp8-block | the declared FP8 decode rows (fp8-block-rows' rows alias it; sm_89 on): E4M3 weights with a scale grid against E4M3 activations per group (DeclaredFp8, ScaleGrid) | WARPS, AHEAD, STREAM (none changes an output's order) |
| decode-nvfp4 | the decoders (an NVFP4 matrix's values in 16 bits or as FP8 rows) | none |

The CUDA structures dispatch through the build's `crit_tuning.h` (gemv-cuda per format, matrix N, K and row count;
the aliases per N, K and row count); the Triton ones read
`_crit_tuning.knobs()`. ROWS, WARPS, PREF, STREAM, BLOCK_N and STAGES choose which rows a block or program takes and
how its loads run, never a row's sum order.

## Build, test, tune

```sh
crit kernels build decode-gemv                                   # for this GPU, default knobs
crit kernels build decode-gemv --arch 80 --arch 86 --arch 89 --arch 90a --arch 100a --arch 120a   # build check
python -m pytest kernels/techniques/projections/decode-gemv/tests -q
crit kernels sweep decode-gemv --model CHECKPOINT --out TUNING_DIR   # or --shapes FILE, --structure gemv-cuda
```

The tests load the kernel with `crit_kernels.build.load("decode-gemv")`: the FP64 bounds for every format at real
widths (INT4 from AWQ- and GPTQ-packed tensors, GPTQ's act order and both zero conventions), every row count alone
and batched bit for bit, both E2M1 decodes (the Triton switch and a plain-target build of the CUDA source), the
decoders' single rounding, graph capture, the FP8 dot GEMV's bounds, its rows' bits at every row count 1 to 16 and
at offsets with and without parts of K, its tile rule and its capture; and a build with other knobs than the defaults
against the default build's bits. The sweep's benches (bench.py) take the checkpoint's
matrices of each structure's format (gemv-cuda: NVFP4, FP8, BF16 from model.matrices(), INT4 from AWQ and GPTQ
checkpoints' qweight tensors, MXFP8 from a shapes file) and check every configuration against an FP64 reference of the
stored values and for row invariance before timing it. Plugins load the kernel with
`crit_plugins.kernels.load_kernel("decode-gemv", ...)`, built with the engine's tuning (`CRIT_KERNEL_TUNING`) or the
default knobs.

The FP8 dot GEMV follows a crit-labs engine's Triton decode GEMV (Apache-2.0), with its tile from a shape rule.
